# GitPulse 产品验证计划

## 当前决策

**状态：继续验证，不启动下一产品主线。**

截至 2026-07-19，公开证据不足以在“定时自动生成”“企业交付集成”“团队配置协作”中选择一条。这个结论是有意的产品门槛，不是待办遗漏：在收到足够的非作者用户反馈前，继续增加功能会放大方向错误的成本。

## 目标用户与问题清单

| 用户层 | 要验证的核心场景 | 必问问题 |
| --- | --- | --- |
| 个人开发者 | 多 Repository 按日/周生成并提交报告 | 当前多久生成一次？哪些步骤最重复？是否需要定时执行？ |
| 团队负责人/管理者 | 按 Author Scope、Repository 和配置方案汇总 | 是否需要多人共享规则？谁维护规则？冲突如何处理？ |
| 企业交付人员 | 固定周期、多格式、命名规则和外部交付 | 报告交到哪里？当前靠什么脚本或人工步骤？是否需要系统集成？ |

每条反馈还需要：发生频率（每天/每周/每月/偶发）、影响（阻塞/高/中/低）、当前替代方案、期望结果、愿意提供的样例，以及是否愿意参加一次试用。维护者不得要求原始 Git 提交、报告全文、工作区路径、凭据或未审查的日志。

## 反馈入口与数据边界

- GitHub Issue Form：`.github/ISSUE_TEMPLATE/product-feedback.yml`，用户主动填写并主动提交。
- 应用内支持入口：设置 -> 诊断 -> “准备支持包”。支持包在本机预览和导出，用户确认后才可导出；“打开 GitHub Issue”只带 Safe Issue Summary，不带附件、事件日志或本地路径。
- 允许记录：公开 Issue URL、用户主动填写的脱敏场景、公开仓库统计、Release 资产下载计数和聚合后的评分。
- 禁止默认记录：应用使用遥测、崩溃自动上报、工作区/Repository 路径、提交内容、报告草稿、身份信息、凭据、完整支持包和云端同步数据。
- 代理指标须带限制说明：clone 可能来自 CI 或开发者，Release 下载可能是重复下载，GitHub 页面流量不能推断应用启动或留存。

## 候选方向与可证伪假设

### 1. 定时自动生成

- 假设：个人开发者或团队会固定周期自动生成报告，并愿意配置本地任务和失败提醒。
- 正向证据：反馈明确描述固定周期、定时触发、失败通知和无人值守需求。
- 反证：用户只需要一次性批量补报，或仍要求每次人工确认内容后再导出。
- 非目标：后台上传、云端调度和默认执行用户脚本。

### 2. 企业交付集成

- 假设：企业交付人员的主要痛点是把报告按格式、命名和目标系统稳定交付，而不只是生成文本。
- 正向证据：至少两名非作者用户提供真实目标系统、格式约束或交付失败样例，并愿意试用。
- 反证：用户只需要本地 Markdown/Word/PDF 导出，或没有稳定的外部系统边界。
- 非目标：云端账户、服务端同步和未经用户确认的外发。

### 3. 团队配置协作

- 假设：团队需要共享 Author Scope、Project Name Mapping、Evidence Detail 和模板规则，并需要版本/冲突管理。
- 正向证据：至少两名团队负责人独立描述共享配置冲突或重复维护，并愿意提供一份脱敏配置样例。
- 反证：现有配置方案导入/导出已经解决主要问题，用户没有实时协作或版本需求。
- 非目标：在没有权限和冲突证据前引入云端配置中心。

## 评分模型

每条候选方向满分 10 分：

| 维度 | 分值 | 评分标准 |
| --- | ---: | --- |
| 需求信号 | 0-3 | 0 无直接反馈；1 相邻描述；2 一条直接反馈；3 多名用户直接反馈 |
| 重复性 | 0-2 | 0 偶发；1 每月；2 每周或更频繁 |
| 试用意愿 | 0-2 | 0 无意愿；1 愿意访谈；2 愿意提供样例或参与试用 |
| 战略贴合度 | 0-2 | 0 偏离 local-first；1 可局部适配；2 直接减少报告交付判断成本 |
| 证据质量 | 0-1 | 0 仅代理指标/单条相邻反馈；1 有可引用的结构化用户输入 |

候选总分至少 `7/10`，且不得在证据质量为 0 时立项。

## 进入实现门槛

下一轮复评必须同时满足：

1. 至少 5 份结构化反馈，其中至少 3 份来自项目作者以外的用户。
2. 至少 2 份独立反馈把同一候选方向列为首要痛点，且频率为每周或更高、影响为高或阻塞。
3. 至少 1 名用户提供脱敏真实样例，或明确承诺参加可回滚的试用。
4. 该候选方向评分达到 `7/10`，并补齐范围、非目标、失败路径和 local-first 数据边界。
5. 复评记录引用 Issue/样例链接和抓取日期；无法公开的内容只记录去标识化摘要。

在门槛满足前，维护者只做验证：发布 Issue Form、邀请真实用户填写、每周去重和记录反证；不实现三个候选方向中的任何一个。

## 下一轮动作

- 通过 README 和 GitHub Issue chooser 引导用户使用结构化 Issue Form；后续 Release notes 继续复用该入口。
- 每周检查一次新反馈，按角色、候选方向、频率、影响和试用意愿归档；不把仓库流量当作用户反馈。
- 达到 5 份反馈或 30 天后，以先到者为复评点；若仍不足，继续验证并保留当前决策。
- 只有复评通过一条候选方向后，创建独立 PRD/任务；定时、企业集成和团队协作不得并行启动。
