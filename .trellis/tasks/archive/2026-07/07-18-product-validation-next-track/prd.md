# 建立用户验证并选择下一产品主线

## Goal

建立不依赖默认遥测的用户验证闭环，并基于可引用证据决定下一阶段是否进入“定时自动生成”“企业交付集成”或“团队配置协作”中的一条主线。

## Background And Confirmed Facts

- 前置的 7 个工程任务已完成并归档，父路线当前为 `7/8`。
- GitPulse 保持 local-first，不引入云端账户、默认遥测或后台数据同步。
- 支持包已提供本地预览、脱敏诊断、用户确认后的本地 ZIP 导出，以及不带附件和本地路径的 GitHub Issue 安全摘要。
- 2026-07-19 GitHub 快照：13 stars、1 fork、1 subscriber、0 open issues；全部历史 Issue 中只有 #1 一条外部功能反馈，内容集中于批量生成、历史补报、按作者/项目拆分和多格式导出。
- v0.5.3 资产下载量为：`gitpulse-latest.json` 50、Windows 安装包 1、Windows 签名文件 1、macOS/Linux 安装包 0。仓库流量为 31 views/16 uniques、619 clones/179 uniques；这些是仓库级代理指标，不能证明桌面应用活跃使用。

## Target Users And Core Scenarios

- **个人开发者**：按日/周从多个本地 Repository 生成报告，并在低活动日补充可审计的事实。
- **团队负责人/管理者**：按 Author Scope 或 Repository 汇总成员工作，并复用脱敏配置方案。
- **企业交付人员**：按固定周期、格式和命名规则导出可提交或归档的报告。

每条反馈必须说明角色、当前工作流、发生频率、影响程度、期望结果和是否愿意提供真实样例或参加试用；不能要求用户上传原始提交、报告、路径、凭据或完整支持包。

## Requirements

- **R1 验证渠道**：提供结构化 GitHub Issue Form，并记录可引用的用户反馈；仓库流量和 Release 下载只能作为辅助信号。
- **R2 主动支持入口**：保留应用内“准备支持包”入口。用户必须先预览和确认，支持包和安全摘要均由本地生成；任何附件提交都由用户在浏览器中主动完成。
- **R3 评估候选主线**：用仓库反馈、Release/仓库使用代理数据和至少一轮结构化用户输入，逐条评估三个候选方向的需求强度、重复性、试用意愿、战略贴合度和证据质量。
- **R4 诚实决策**：只有候选方向达到量化门槛时才进入实现；当前证据不足时明确记录“继续验证”，不得用 clone、下载或单个相邻需求伪造选择。
- **R5 数据边界**：验证记录只保存用户主动填写的脱敏内容、公开仓库指标和 Issue 链接；不得增加默认遥测、自动上传、云端账户或服务端同步。

## Acceptance Criteria

- [x] AC1：产品验证计划、目标用户、问题清单、数据边界和决策评分模型入库。
- [x] AC2：至少有一条可引用的结构化反馈；证据不足时明确选择“继续验证”。
- [x] AC3：形成带量化门槛、非目标和下一轮行动的暂缓决策，而不是伪造已选主线 PRD。
- [x] AC4：父路线完成审计所需的支持包、Issue 入口、证据快照和独立提交记录齐全。

## Decision

截至 2026-07-19，三个候选方向均未达到 `7/10` 的实现门槛，当前决策为 **继续验证，不启动下一产品主线实现**。后续只在 `docs/product-validation-plan.md` 的门槛全部满足后重新评分并选出一条主线。

## Out Of Scope

- 不在本任务实现定时任务、企业系统连接器或团队实时协作。
- 不把仓库 clone、Release 下载或 GitHub 页面流量解释为桌面活跃用户数。
- 不收集默认遥测，不自动上传支持包，不在 Issue URL 中附加本地文件或日志。
