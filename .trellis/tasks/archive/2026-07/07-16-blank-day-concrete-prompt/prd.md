# 收紧空白日补写默认提示词

## Goal

让“空白日补写”基于历史 Git 提交推导更具体、更可能发生的后续开发事项，优先生成现有功能延伸、缺陷/回归修复、边界兼容、测试补强或接口/数据流完善，而不是只写“跟进、排查、推进、整理”等无法核对的空泛动作。

## Background

- 当前 Rust system prompt 和前端可编辑默认 Prompt 都明确要求优先使用“跟进 / 排查 / 推进 / 联调 / 整理”，这是空泛输出的直接原因。
- 历史提交线索已包含项目/仓库前缀、提交主题和证据上下文，足以要求模型把每条草稿锚定到具体历史对象。
- 补写仍是可编辑草稿，不得伪装成目标日真实提交，也不能虚构上线、验收、业务结果、百分比或从未出现的模块。

## Requirements

- Rust `blank_day_system_prompt` 与前端 `DEFAULT_BLANK_DAY_USER_PROMPT` 必须同步反转旧偏好，禁止把“跟进 / 排查 / 推进 / 整理 / 联调”单独作为事项主体。
- 每条输出必须能从历史线索指出一个具体锚点，例如已有功能、接口、数据流、页面、脚本、测试、异常路径或提交中出现的技术对象。
- 优先生成最可能的代码级延续：补齐已有功能分支、修复潜在缺陷/回归、完善异常和边界处理、补测试与验证、改善兼容性或衔接现有接口/数据流。
- 若确需使用“排查/跟进”等动词，必须同时写清被处理的具体对象、问题模式和拟采取的动作，不能只写过程性表态。
- 多条输出应覆盖不同历史线索或不同具体动作，避免同义改写和注水。
- 保留现有项目前缀规则、恰好 N 条短要点、正式语气和不可核实结论禁令。
- 用户自定义 Prompt 仍可覆盖默认偏好；“恢复默认”和用户留空时的 Rust 回退语义必须一致。

## Acceptance Criteria

- [x] Rust 单元测试证明 system/user prompt 包含具体锚点、功能延伸/缺陷修复/测试补强要求，并明确拒绝空泛动作。
- [x] 前端默认 Prompt 展示相同的具体化约束，`scripts/frontend-smoke.mjs` 覆盖关键文案。
- [x] 原有项目前缀、条数、不可伪装真实提交和禁止虚构结论约束保持不变。
- [x] `cargo fmt -- --check`、相关 Rust 测试、`npm run build`、前端 smoke、相关 Playwright 与 `git diff --check` 通过。

## Out of Scope

- 对 AI 输出增加后处理分类器或关键词硬删除。
- 修改空白日补写 UI、历史标记、素材扫描、仓库选择、模型参数或 API 调用方式。
- 保证模型一定命中真实未来工作；本次只提高默认提示词的具体性与历史锚定强度。
